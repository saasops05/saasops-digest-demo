Automation 1

Release digest — GitHub → Slack

On release / tag: merged PRs → Features / Fixes / Chores with authors + links → facts-only Slack digest. Human reviews, then sends. No LLM inventing impact.

This week

  1. Pick one repo that ships tags regularly.
  2. Wire the Action (or run the fixture locally first).
  3. Ship one digest to a private Slack channel.
  4. Keep the footer: auto-generated · verify before broad distribution.

Automation 2

Support triage — inbound → draft issue + Slack gate

Inbound message → rules-based category / priority / confidence → GitHub issue draft + Slack approval card. Approve / edit / reject before anything is filed. Never invents ARR-at-risk — only what’s in the message.

This week

  1. Capture 5–10 inbound samples; list labels you already use.
  2. Write keyword → category / priority rules (bug / billing / how-to).
  3. Walk the live fixture, then point rules at one mailbox or Slack channel.
  4. Require the Slack gate before any GitHub issue is created.

Automation 3

Reply drafts — founder voice, never auto-send

Inbound sales/support email → short reply draft in your voice → held for approve / edit / reject. Guardrails block invented ARR, prices, and dates. Even “approve” just hands you the draft — you copy it into your mail client.

This week

  1. Pick one mailbox or channel where the same asks keep landing.
  2. Write a short founder-voice note + approved link list.
  3. Drafts only — nothing auto-sends.
  4. Log what you edited so the next version gets sharper.

Order of operations

  1. Digest — visible win, easy demo, Action ready for the release path
  2. Triage — less copy-paste noise; Slack gate before GitHub
  3. Reply drafts — careful; human always owns send

Don’t stack all three in week one. Ship one, keep the human gate, then add the next.
